# 协作规则（我自己的备忘）

> 这份是**给我（智能体）看的**工作约定，不是给用户的功能文档。
> 用户 2026-11-07 明确要求，之后每轮开始时按此执行。

## 1. 触发式工作，不做例行巡检

除非用户说「检查文档更新 / 更新新内容 / 看看有什么要做的」这类指令，**默认不要**主动跑
`cardspec.py --pending` 并开始实现待办。

用户只发一条具体指令（例如「改一下某张卡」「写个文档」「启动游戏」）时：
- 只做那件事；
- 不顺手把攒着的待实装内容做掉。

理由：单批内容扩展太碎，用户希望自己控制节奏。

## 2. 只处理「被标记」的内容

需要我实现/修改/删除的依据，**只看设计表里的状态标记**：

| 标记 | 我的动作 |
|---|---|
| `待实装` | 实现 |
| `待修改` | 按备注改 |
| `待删除` | 删代码 + 删表里这一条 |
| `已实装` | **不看** |

## 3. 已实装条目的「数值差异」不归我管

用户在反复调整数值时会直接改设计表（或自己改代码）。因此：

- 标记为 `已实装` 的卡牌，**表里的数值和代码不一致时，不要改、不要提示**；
- 也不要因为数值不同去重新实现或对齐；
- 文案（措辞）不一致仍然值得提示，数值不一致不算问题。

工具侧注意：`check_text_matches` 已经把数字剔除后再比对，所以数值不同不会误报——保持这个设计。

## 4. 有需要才跑校验

`cardspec.py` 的默认全量校验只在以下情况跑：
- 我刚改过代码/设计表（改完自检）；
- 用户要求检查；
- 我怀疑状态标记或结构有问题。

平时不必每轮跑一遍然后罗列一堆「建议」。

## 5. 每轮收尾仍然要做的（属于交付质量，不是巡检）

- 改完代码后：编译；能部署就部署（游戏开着则说明需要重启）；
- 用户没要求启动游戏时**不要启动**；
- 改动提交 git。

## 6. 用户偏好速记

- 游戏内文本用他写的原文，不改写、不加修饰；`<br>` = 换行，`{Amount}` / `{N*Amount}` 是变量写法。
- 描述结尾要有句号、中文里不留空格（`normalize_text.py` 自动处理）。
- 数值调整他自己也能做，参见 `docs/card-code-guide.md` 和 `tools/apply.ps1`。
- 不要擅自扩大改动范围；有歧义先问。
